# Claim-Number and Approved-Document Attribution Assessment

**Date:** 17 September 2026  
**Author:** Manus AI  
**Scope:** Read-only test of an automated preservation hypothesis before any reset decision. No claim, document, user, assessment, configuration, or database record was changed. No claim number, claim ID, source filename, storage location, or other direct record is included.

## Conclusion

The proposed automated approach does **not** identify a reliable protected set close to the owner’s expected approximately 70 claims.

The document-ingestion claim-number format, `DOC-YYYYMMDD-XXXXXXXX`, is a real system-generated format. However, it accounts for only **97 of 18,064** claims in the three dashboard sections. The remaining **17,967** claims are not evidence of manual entry: they include the known high-volume `TEST`, `CLM`, and `WB` families. Therefore, “non-DOC” is not a usable proxy for a manually created owner claim.

After excluding those known high-volume families and `DOC`, only **15 rare-prefix claims** remain. That is far from approximately 70. It also cannot be assumed to be an owner set because some rare prefixes are demonstrably generated by application logic, and several rare-prefix claims share batch timing. The owner-identified `LIVE-RUN` family contains exactly one claim, which is consistent with the owner’s stated example but does not generalise to the expected total.

The four fully extracted, validation-approved `claim_form` source documents map to **four** KINGA Complete claims with a single `COR` prefix. They are non-marker claims, but three were created on days that also created synthetic-marker users and the group has synchronized pairs. The four claims are not a credible approximation of 70 and must not be used to infer a broader preservation rule.

> **Result:** no automated protected set is proposed. The evidence supports only the two options the owner specified: a full reset with no claim preservation, or reconsideration of an owner-reviewed exact list. The assessment does not authorise either option’s execution.

## What the DOC format actually means

The document-ingestion router contains an explicit generator for `DOC-YYYYMMDD-XXXXXXXX`: a UTC date plus eight random hexadecimal characters. The format is generated when a claim is created through that route. [1]

This explains the 97 standard-DOC claims and confirms that the pattern is **system generated**, not a manual-number marker. It does not imply that non-DOC claims were manually typed. Several other application and seed paths use different reference families. For example, source code generates `KNG` references in a database helper under a documented fallback path. [2]

## Narrow rare-prefix result

Excluding `CLM`, `TEST`, `WB`, and `DOC` leaves 15 claims across the three dashboard sections. The observed rare-prefix groups are diverse rather than one coherent owner-defined family. They include four `COR` claims, four `TENANT` claims across two sections, and single-claim families including `FT`, `KNG`, `LIVE`, `PLATFORM`, `RPT`, and `VP`.

All 15 have non-marker claimants, but that does not make them real owner claims. The prior population assessment established that a missing literal test marker is not a reliable distinction. The rare-prefix groups also include synchronous pairs: the `COR` and `TENANT` groups each have creation minutes containing two rare-prefix claims, and the two `PLATFORM` claims share a creation minute. The `KNG` prefix has a known application generator. [2]

The `LIVE-RUN` family contains one claim, and it is KINGA Complete. This supports preserving the particular owner-identified claim if a later preservation list is used. It does not establish that other rare prefixes belong to the owner, nor does it create a 70-claim set.

It also falls far short of the expected approximately 70 claims.

## Decision boundary

No valid automatic rule can be derived from lifecycle state, claimant marker, timestamp cadence, document status, or claim-number format without risking arbitrary preservation or deletion. The earlier evidence already showed that lifecycle and non-marker groups reproduce synthetic timing patterns. This assessment independently shows that the claim-number and approved-document leads do not overcome that problem. [3] [4]

The defensible options are therefore limited to the owner’s stated alternatives:

1. **Full reset with zero claim preservation.** The owner would recreate a clean test corpus after the reset. This would require a separately reviewed destructive-change package defining the exact scope, dependency handling, encrypted archive and restore rehearsal, transaction boundaries, and independent postflight checks. It is not authorised by this assessment.
2. **Owner-reviewed exact preservation list.** An owner can identify the claims to keep through the UI, including the known `LIVE-RUN` claim. The list would then undergo a read-only direct-match and dependency-closure check before a reset package is proposed.

No third option is proposed because it would overstate the strength of the available evidence.
