# KINGA Report Generator Raw-SQL and Canonical-Layer Findings

**Date:** 20 August 2026  
**Scope:** Static source audit only; no database access, data changes, schema changes, or report-behaviour changes.  
**Purpose:** Identify report-generator database reads that bypass the documented `resolveClaimRecord()` / `normaliseReportData()` canonical layer.

## Finding Summary

The three claim-report tiers are generated by live renderer functions that each open a MySQL connection and independently execute raw SQL. The new cross-tier regression proves that one controlled fixture renders the same **REVIEW** decision, fraud score **57**, and market value **$54,321.00** in CL, CI, and FR. It does **not** establish that those generators use the canonical layer; the code inspection confirms they do not consistently do so.

> `normaliseReportData()` is documented as the single transformation layer for monetary, fraud, and verdict values. The claim-tier renderers do not call it directly. [1]

The raw-SQL inventory contains report queue, scheduling, administration, and non-claim report modules as well as rendering modules. This report distinguishes direct **claim-report canonical-layer bypasses** from other raw-SQL uses that need normal service-layer review but are not instances of the CL/CI/FR shared-value problem.

## Direct Claim-Tier Findings

| Renderer / tier | Raw-SQL reads | Canonical-layer status | Finding |
|---|---|---|---|
| **Claims Ledger (CL)** — `generateReportHtml("claim.assessment", ...)` | Claim + latest assessment (`reportDefinitions.ts:201`); damage components (`:257`); quotations (`:262`); quote lines (`:274`) | **Bypasses `normaliseReportData()`** | Directly reads `fraud_score`, `vehicle_market_value`, `workflow_state`, assessment costs, recommendation, and several JSON payloads. It independently derives and formats report fields. |
| **Claims Intelligence (CI)** — `generateClaimsIntelligenceReport()` | Claim + assessment (`claimsIntelligenceReport.ts:40`); quotations (`:63`); quote lines (`:73`); documents (`:85`); vehicle history (`:96`); pre-loss condition (`:104`) | **Bypasses `normaliseReportData()`** | Directly reads and derives fraud, market-value, recommendation, repair-to-value, quote, document, and history state. |
| **Forensic Report (FR)** — `generateForensicDecisionReport()` | Claim + assessment (`forensicDecisionReport.ts:37`); quotations (`:60`); documents (`:71`); pre-loss condition (`:80`); audit events (`:96`); disputes (`:107`) | **Bypasses `normaliseReportData()`** | Directly reads and derives the same shared core fields while adding forensic-specific evidence. |
| **Evidence governance panel**, consumed by CI/FR | Evidence ledger (`evidenceGovernancePresentation.ts:121`); findings (`:129`); gaps (`:137`) | **Supplementary read path, not normalisation** | This supports report evidence presentation. It does not itself resolve shared decision/fraud/market-value authority. |

The CI report has an additional documented drift risk: its claim assessment report path reads `parts_cost`, `labor_cost`, driver, weather, and GPS fields through raw SQL while those fields are not modeled by the main Drizzle schema. This was separately recorded in the schema-drift classification and remains **documented only** in this branch.[2]

## Interpretation

The raw-SQL use is not, by itself, a defect. Reports need authorized persistence reads, and non-claim reports need their own domain-specific aggregations. The defect pattern is narrower: **multiple renderers independently selecting, interpreting, or recomputing fields that are meant to be single-authority claim decisions.**

This branch deliberately does not refactor any raw SQL. It records the complete static inventory and adds a regression fixture so a future refactor has an executable baseline. Any remediation must preserve tenant predicates, source/evidence distinction, the approved L1/L2 policy, and current report-access rules.

## Recommended Follow-Up (No Change in This PR)

1. Define a typed, tenant-bound canonical claim-report projection that carries shared decision status, fraud score, market value, and their sources to CL, CI, and FR.
2. Classify each current direct query field as either canonical shared state, tier-specific evidence, or report-local presentation data.
3. Replace only shared-state re-derivations with the projection in a separately approved remediation package; preserve tier-specific forensic/evidence reads where justified.
4. Extend the new regression to additional shared fields only after their canonical authority is explicitly defined.
