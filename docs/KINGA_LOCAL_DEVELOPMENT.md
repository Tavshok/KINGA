# KINGA Local Development Manual

## 1. Preconditions

Install a compatible Node.js runtime, pnpm, Git, and the MySQL-compatible test database tooling required by the current branch. The repository contains `.env.example`; copy it to a local uncommitted environment file and supply only approved non-production values. Never commit `.env`, connection strings, OAuth secrets, provider tokens, customer documents, or production data.

## 2. Setup sequence

```bash
git clone <approved KINGA repository URL>
cd KINGA
pnpm install --frozen-lockfile
cp .env.example .env
# Populate only approved non-production placeholders/credentials.
pnpm check:conflicts
pnpm check
pnpm test
pnpm dev
```

`pnpm dev` starts the development server through `tsx` and `server/_core/index.ts`; the client build is provided through the Vite integration. The effective bind/port is environment/runtime controlled. Do not hard-code a production port in feature code.

## 3. Database and migration safety

The source schema is `drizzle/schema.ts`; migration configuration is `drizzle.config.ts`; `pnpm db:push` invokes Drizzle generation/migration scripts. Before any schema work, read [KINGA_DATABASE_MANUAL.md](./KINGA_DATABASE_MANUAL.md), `docs/SCHEMA_MIGRATION_DRIFT_AUDIT.md`, and `docs/SCHEMA_MIGRATION_REMEDIATION_PLAN.md`. Do not run a migration against production or use an undocumented database connection.

The exact local seed dataset and a fully automated local database bootstrap are **[NOT VERIFIED IN CODEBASE AS A SINGLE AUTHORITATIVE WORKFLOW]**. Treat scripts in `scripts/` as tools to inspect, not automatic permission to run against a real environment.

## 4. Debugging

Use the server/client logs generated by the active environment. Start diagnosis with the concrete failing procedure, route, import or test identifier; trace from `client/src/App.tsx` / component hook to `server/routers.ts`, the feature router, service/resolver, and schema. For a tenant issue, prove session/tenant/object authority in that order. For a report issue, compare the canonical resolver/model inputs before adjusting output formatting.

## 5. Reset and recovery

Before risky work, create a review branch and commit small, auditable steps. Use ordinary pull requests and current-main refreshes; do not force-push, rewrite shared history, delete an evidence branch, or use destructive database cleanup. The documented repository contains Docker artefacts, but the exact mandated local recovery/runbook environment is **[NOT VERIFIED IN CODEBASE]**.
