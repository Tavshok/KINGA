# P0-B1 Integration Wrapper Reintroduction Guard

**Date:** 24 September 2026
**Package:** P0-B1 Integration Wrapper Reintroduction Guard
**Status:** Merge-ready; pull request review pending
**Scope:** Server-side authorization-ordering regression controls only

## Purpose

This is a narrow, independent integrity package discovered by the final shared-middleware audit that followed P0-B1 Residual Authority Hardening (PR #152). It does not modify fraud policy, report content, data, schema, deployment, P0-B1-Client, P0-B2, or P0-B3.

The paused P0-B1 integration branch contains an unmerged historical commit that defines `p0FraudExecutiveProcedure`. That middleware throws a fraud hold before route-local authorization. It wraps Executive Operational Detail and the three executive fraud analytics routes. If rebased unchanged, it would undo the authorization-before-hold ordering established by PR #152.

## Root cause

The repeatable defect is architectural rather than a series of unrelated route mistakes. The canonical throw helper can be called from any server code without an authorization capability, while tRPC permits a procedure middleware to terminate a request before a route handler executes. TypeScript models the resulting context shape, but it does not model that the correct tenant, resource, selected-tenant, and cross-tenant-audit sequence has completed for the particular route. `insurerDomainProcedure` also deliberately permits a tenantless platform administrator to continue for routes that accept and validate explicit tenant selection. That valid flexibility means a generic fraud-hold middleware cannot safely stand in for every route's authorization work.

A type-branded authorization token would require redesigning every route-specific authorization API and still could be forged with casts or bypassed through a second helper. It would therefore create a misleading assurance if added as a small patch. The appropriate near-term structural control is a mandatory, repository-wide source governance test that runs through the existing guarded Vitest suite and hosted Quality Gate.

## Controls added

### Repository-wide middleware governance test

`server/p0B1FraudHoldMiddlewareGovernance.test.ts` parses non-test, non-script, non-generated TypeScript sources below `server/` with the TypeScript compiler API. It centrally unwraps transparent parenthesized expressions before classifying a binding, a callback/factory, a canonical hold callee, a `TRPCError` constructor, or the callee of a `.use(...)` / `.middleware(...)` call. It treats a direct `*.middleware` reference, including an alias or destructured `middleware` binding, as a first-class factory binding and resolves it at the factory-call source position. It resolves inline and parenthesized middleware callbacks, a module-declared identifier callback passed to `.use(...)`, a direct `t.middleware(...)` wrapper, and a module-declared identifier bound directly to `t.middleware(...)`. Module-level named function declarations are pre-registered as hoisted bindings before the source-order walk, while later assignment history remains source ordered. Its binding history intentionally records module-scope cells only, so unrelated nested declarations cannot overwrite a callback or helper captured by a module-level procedure. Within each inspected middleware callback, it resolves direct callback-local aliases of the canonical hold and `TRPCError` helpers without descending those aliases into nested function bodies or applying them when an enclosing block shadows the name, preserving lexical shadowing. It resolves a callback or callback alias at the source position where `.use(...)` captures it, rather than using a later reassignment. Direct helper calls use the final module-level simple identifier binding established during module initialization, because the registered callback reads that helper cell when it runs. Its direct binding map is source-order aware for simple identifier assignments. It then rejects either of the following:

1. An imported canonical P0-B1 fraud hold builder or throw helper, including named-import aliases, namespace references, direct aliases of namespace objects, destructured namespace bindings, and direct local rebindings.
2. A local `TRPCError` whose payload combines `PRECONDITION_FAILED` with fraud-specific text, including named-import aliases, namespace references, direct aliases of namespace objects, destructured namespace bindings, and direct local rebindings.

The test proves that the detector rejects inline and parenthesized inline, parenthesized `.use` and `t.middleware` callees, parenthesized module callback and factory, parenthesized canonical callee and local `TRPCError` constructor, named-callback including a hoisted module declaration, direct callback-alias, callback-local canonical and `TRPCError` aliases, reassigned callback/helper, post-registration reassignment, direct/named/aliased/destructured `middleware` factory forms, namespace, direct namespace-object alias, direct destructured namespace binding, named-import alias, and local-rebinding variants. It also proves that nested function and block bindings cannot overwrite a captured module helper or cause a false positive through a shadowed nested callback helper; that the scan excludes test, script, generated, build, coverage, and dependency paths; and that an authorized direct route hold remains permitted. Because it is an ordinary guarded Vitest test, the existing hosted Quality Gate executes it on every pull request and `main` push. The test intentionally does not prohibit canonical holds in route handlers, because the required authorization is route-specific and must execute there before the hold.

### Executive route reintroduction guard

`server/p0-package-3-executive-router.test.ts` now parses the single top-level exported declaration `export const executiveRouter = router({...})` with the TypeScript compiler API. It rejects every spread assignment in that router object, so a later object spread cannot override a compliant held route. It requires the canonical hold to be imported from `../evidence-governance/p0FraudDecisionHold`, rejects `p0FraudExecutiveProcedure`, and rejects any callback-local shadow of a required authorization, audit, or hold identifier. It requires each held route to have a terminal held-route shape: analytics routes contain only `requireExecutiveFraudTenantScope(ctx)` followed by the canonical hold; Operational Detail contains only immutable scope resolution from route `ctx`, **awaited** validation of that exact scope, its audit under the actual cross-tenant branch with that exact `ctx` and scope, and then the canonical hold. The cross-tenant branch must itself contain exactly the **awaited** audit call, preventing both scope mutation and an unresolved audit promise between branch entry and the hold. It rejects any additional top-level statement, including an early return that could make the hold unreachable. It requires `scope` to be the single immutable `const` bound directly to `resolveP0TenantScope`, and rejects any additional `scope` or `ctx` binding in the callback. It does not descend into nested function bodies or arbitrary branches, so an uninvoked or non-executing authorizer cannot satisfy the control. Regression fixtures prove that comments/strings, later decoy objects, nested shadowed `executiveRouter` declarations, router spread overrides, uninvoked nested authorizers, non-executing conditional authorizers, unawaited validation, an incorrect or unawaited audit branch, scope mutation, mutable/copy/forged/shadowed scope, callback-local fake holds, and early-return unreachable holds cannot satisfy this invariant.

## Deliberate boundary

This package prevents the specific systemic reintroduction mechanism without claiming that static source analysis replaces caller-level authorization tests. Its repository-wide AST scan deliberately covers module-level ordinary direct callbacks, direct identifier aliases, simple identifier reassignments, direct or named `t.middleware(...)` composition, local helper calls, and fraud-hold import/rebinding patterns including direct namespace-object aliases and direct destructured namespace bindings. It distinguishes callback capture at `.use(...)` registration from later module helper-cell resolution during execution. It is not a whole-program proof against arbitrary dynamic dispatch, cross-module callback factories, computed/reflection-based wrapper construction, or deliberate unsafe casts. The existing behavioral tests remain the proof that unauthorized roles, tenantless platform administrators, cross-tenant selection, and zero post-hold data reads behave correctly at runtime. A larger type-capability redesign is logged as a future architectural option, not silently added here.
