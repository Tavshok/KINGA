## Purpose and intentionally paired scope

This first-tier package closes the two live dashboard defects found by the final composed P0-B1 review. They were implemented and reviewed together because both relied on the same unsafe pattern: a hold-aware or safe-looking hook existed beside a separate raw server route that actually supplied the mounted dashboard.

| Surface          | Live unsafe path before this package                                                                                                                                                                                                                                               | Closed boundary                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Risk Manager     | Parallel calls to `claims.byStatus`, `claims.getActiveClaims`, and `claims.getFinancialDecisionQueue` returned raw stored fraud fields. The browser classified, colour-coded, counted, and displayed them; `claims.approveClaim` remained wired as a generic error/toast workflow. | A role- and tenant-gated `claims.getRiskManagerOperationalClaims` server allowlist is the page's only query. It does not select stored fraud fields. Risk Manager is denied before DB acquisition on the two raw legacy routes; the retired financial queue returns only the canonical hold. The page contains no raw fraud query, field, score band, or approval command. `approveClaim` now enforces the actual claims-manager/executive command policy before claim lookup and the P0 hold. |
| Claims Processor | The mounted screen called `workflowQueries.getClaimsByStatus`, which returned full rows with raw fraud fields, while a separate `claims.getProcessorQueue` hold-capable hook was unused. Browser code rendered the raw score as High/Medium/Low.                                   | The unused decoy hook and browser score badge are removed. The real status-feed route server-projects out `fraudRiskScore`, `fraudRiskLevel`, `fraudFlags`, and `earlyFraudSuspicion` for a `claims_processor` and for both canonical platform-admin roles. The row order and pagination metadata are retained.                                                                                                                                                                                |

This package does **not** claim to close raw fraud publication across every other dashboard or role. The final review's remaining cross-estate routes, including other callers of `claims.byStatus`, `claims.getActiveClaims`, and `claims.allForTenant`, remain separate narrow packages. The separately approved B-G3 proposal is still required to discover raw fraud sources outside the canonical hold-consumer inventory.

## Authority and ordering invariants

1. The new Risk Manager endpoint performs role authority, then a concrete tenant requirement, then DB access and the allowlisted projection.
2. A Risk Manager direct caller receives `FORBIDDEN` from raw `byStatus` and `getActiveClaims` before a DB handle is opened. A hold does not mask that raw-route denial.
3. `approveClaim` performs session → approved actor (`claims_manager` or `executive`) → tenant-owned claim → canonical P0-B1 hold → no quote, DB write, audit, or notification work.
4. The Claims Processor's actual mounted source is protected at the server response boundary. Browser removal alone is not relied on.
5. `isAdminRole()` is used for Claims Processor projection; it covers both `admin` and `platform_super_admin` and avoids a privileged raw-response bypass.

## Adversarial review

The initial independent review **BLOCKED** a real hole: `platform_super_admin` did not match an exact `role === "admin"` check and could receive raw Claims Processor status rows. The smallest correction replaced the exact string comparison with the existing `isAdminRole()` predicate and added genuine `workflowQueriesRouter.createCaller` coverage for both admin roles.

A fresh independent re-review then **APPROVED** the correction. It confirmed that the caller test executes the real router and insurer-domain middleware, mocks only the database chain, verifies all four raw fields and a sentinel value are absent, and retains count/pagination/order assertions.
